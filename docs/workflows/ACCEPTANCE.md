# Workflow acceptance

A screen alone does not satisfy a business workflow. Each supported command has server authorization, transactional database writes, validation, audit/outbox records and retry deduplication.

| Workflow | Implemented slice | Boundary |
|---|---|---|
| Purchase to stock | Draft multi-line PO in purchase units (exact base conversion) → submit → independent approval (not creator/submitter) → per-line GRN under a delivery note into an active RAW warehouse → quarantine lot per line → incoming QC (fail reverses stock/GRNI and reopens the line) → usable lot → supplier invoice matched to released receipts with quantity/price variances (GRNI released at receipt cost, price variance to PURCHASE_PRICE_VARIANCE, payables = billed) ; cancel with nothing received, close short with reason | Requisitions/RFQs, supplier price lists, payment runs and inventory revaluation of price variances later |
| Supplier return | Return released stock of a receipt lot (≤ received − returned, ≤ unreserved) with reason and debit note → stock out at lot balance value → Dr GRNI (part not yet invoiced) / Dr ACCOUNTS_PAYABLE (part invoiced, debit note), Cr RAW_INVENTORY → PO line returned grows; posted returns immutable | Return shipping documents and supplier credit-note reconciliation later |
| Planning to purchase | MRP shortages → draft POs in one request, one per preferred supplier (last active supplier the item was ordered from) plus one supplier-less draft the planner completes; MRP incoming = open base quantity of APPROVED/PARTIAL lines | Lead-time offsetting, MOQ and supplier price lists later |
| Sales to delivery | Draft multi-line SO → confirm (credit-limit warning) → MO per SO line from approved BOM → reserve → issue → start → output → final QC → finished stock → per-line partial/full dispatch → revenue/COGS per delivery; cancel (no delivery, no production in progress) or close short | Quotations, blocking credit control, taxes and shipping integration later |
| Customer return | Return against a delivery (≤ delivered − returned) → quarantine lot at delivered cost → reversing revenue/receivable and COGS journals → RETURN inspection → pass restocks / fail holds | Replacement shipments are new orders; credit notes as documents and cash refunds later |
| Material consumption | FIFO reservations → authorized issue → negative raw ledger → positive WIP value | Exact snapshot issue only; unplanned consumption requires a future controlled variance workflow |
| Partial production | Partial good/scrap output → proportional cost allocation → retained WIP → final output → zero WIP | Conversion costs entered per posting; no implicit whole-order cost allocation |
| Quality failure | Incoming failure → supplier return reversal (recorded on an automatic NCR); any failed inspection → held lot + NCR; plan-driven inspections fail on a critical characteristic out of specification | Unsafe dispatch remains blocked until a disposition releases stock |
| Nonconformance disposition (V12) | NCR (automatic or manual; manual on a released lot holds it) → partial dispositions ≤ affected quantity: concession (independent approval) / scrap (QUALITY_SCRAP, QUALITY_LOSS) / return to supplier (warehouse posts the SR document) / rework (RW order → output lot in quarantine → re-inspection releases it) → DISPOSITIONED (hold lifted, MO may complete) → CLOSED | Rework orders cannot be cancelled once opened (recall holds across a genealogy: V14) |
| CAPA (V12) | CAPA from NCRs or standalone → root cause (6M + five whys) → corrective/preventive actions with owners and due dates → start → all actions done → verification by someone other than the owner → closed (or reopened when not effective) | Notifications for overdue actions are attention counts only |
| Genealogy trace (V14) | Any lot, MO, GRN, PO, SO, delivery reference or supplier + receipt dates → backward to receipts/suppliers through every semi-finished level, transfers, rework and customer returns → forward to every order that consumed it, output lots, transfers, rework, deliveries per customer, returns, supplier returns, scrap, maintenance issues and adjustments, with quantity and date per link; depth 1–30, cycle-safe | Serial numbers and expiry/FEFO not modelled; at most 2,000 lots per direction |
| Recall (V14) | Open from suspect lots or supplier receipts (scope forward or forward + siblings) → affected lots/shipments/customers computed → recalculate while open → contain: RECALL NCR per released lot in stock (V12 hold; already-held lots listed) → snapshot frozen → notify each customer (date, contact, notes) → CSV notification list → close when all notified and every held lot dispositioned, or override by a different quality user with a reason | No e-mail sending; lots that were already held at containment are not re-held when released later (flagged in the drawer) |
| Local operations | Same local API/PostgreSQL transaction boundaries | Browser offline queue and cloud reconciliation not implemented or verified |
| Costing | Actual FIFO materials + entered labour/machine → WIP/finished/scrap → dispatch COGS | Manufacturing subledger; full finance and statutory statements later |
| Multi-level BOM | Semi-finished BOM approved first → parent BOM approved (no cycle at any depth) → explosion/where-used/cost roll-up through all levels → copy approved revision to draft → edit → compare → approve | Alternative components, phantom BOMs, effectivity dates and engineering change orders later |
| Parent/child production | Parent MO (draft/approved) → child MOs for semi-finished shortages (due lead time before the parent) → independent approval of each child → reserve/issue/start/output → final QC releases the SF lot into the raw store → parent's ordinary reservation consumes it | Children are not rescheduled or cancelled automatically when the parent changes; capacity is not checked |
| Breakdown to repair (V11) | Operator reports a breakdown (open BREAKDOWN downtime + corrective work order) → a different planner approves (and may schedule) → technician starts (machine MAINTENANCE; refused while an MO is in progress on the machine) → checklist/findings, labour (journalized), spare parts issued FIFO and unused parts returned → complete (machine IDLE, downtime closed) | No approval-policy threshold for maintenance; machine RUNNING/IDLE transitions from production belong to routings (V10) |
| Preventive maintenance (V11) | Plan per machine (calendar days and optional run hours) → due/overdue list → idempotent generation of scheduled preventive orders → start/complete → plan rescheduled from the completion date; cancelling skips the occurrence; meter readings pull run-hour plans forward | Run hours are entered manually (not derived from production yet); generation is a command, not a background job |
| Downtime analysis (V11) | Report/close downtime with reason and planned flag (no overlap per machine) → append-only corrections → Pareto by reason, downtime minutes, MTBF/MTTR per machine for a period | MTBF on shift working time less downtime in it (V16; around the clock without a calendar); OEE availability is V15 |
| OEE and utilization (V15) | Shift calendar + planned stops → planned production time → logged run time (availability) → ideal cycle time × reported count (performance, capped) → good / total (quality) → OEE = A × P × Q per work center and business day; time-weighted plant/week roll-ups; loss waterfall, six big losses, downtime Pareto, quality losses; untimed output and unrecorded days reported as coverage, never as 0 %; planner closes completed days (idempotent) and recalculates with a reason (history kept) | No telemetry or automatic counts; counts belong to the day they are reported; start-up rejects not separable; demo history is backfilled on marked orders |
| Multi-level MRP | Open MO demand → semi-finished netting (stock, QC stock, open/child MOs, safety stock) → planned production → raw/packaging gross demand → netting against stock and incoming purchases → purchase recommendations with order dates, pegged to driving orders → "Create MO" / "Create purchase" | Infinite capacity, lot-for-lot, single bucket per item; sales-line demand for finished goods is not exploded |
| Routing to operations (V10) | Draft routing (operations, work centers, alternates, setup/run minutes, crew, skill, inspection point) → approval by another planner (not author or last editor) → current revision → new MO snapshots it into PENDING operations (planned minutes for the order quantity) → issue readies operation 1 → start (first start starts the order) / setup done / pause / resume / report / finish on the Shop floor, strictly in sequence → time logs per SETUP/RUN interval → output posting limited to the last operation's good quantity, final output after every operation is done | Overlapping operations, splitting an operation across work centers, rescheduling (V13) and labour/machine cost from time logs later |
| Shift calendars (V10) | Shift patterns (overnight, one break) → calendars (plant default, per work-center assignment) → holidays and overtime → available minutes per work center and day from one service (`routing.CalendarService`) | No history of calendar changes; no per-operator rosters |
| Skills (V10) | Skill catalogue → user levels with certification expiry → operations requiring a skill start/resume only for a qualified user; PLANNER/ADMIN override with a recorded, audited reason | No training records or automatic expiry reminders |
| Two-step sign-in (V17) | Profile menu → set up (setup key or `otpauth://` link in an authenticator app) → confirm with password + code → ten recovery codes shown once → next password sign-in stops at the code screen (authenticator or recovery code) → workspace; administrators of a real workspace must set it up before working; an administrator resets a lost phone | No QR image, passkeys or email recovery; no `MFA_ENCRYPTION_KEY` rotation; code attempt limits in memory per process |

## Defined critical outcomes

1. Competing final-stock reservations: one winner, losing transaction rolls back, no oversell.
2. Duplicate completion key: exact prior result, one production posting.
3. New BOM revisions: approved versions cannot mutate; existing order snapshot remains fixed.
4. Lost HTTP response during material issue: retry same key; successful prior issue is returned. Network fault injection is still pending.
5. Quality-held dispatch: rejected transaction with no stock/accounting side effects.
6. Extra material use: unsupported additional-issue command; no uncontrolled posting path. Consumption variance approval is future scope.
7. Partial output: unfinished quantities/cost remain in WIP; final output clears it.
8. Damaged supplier receipt: incoming failure returns the lot and reverses clearing; PO remainder reopens.
9. Replayed local command: deduplicated by owner/key/action/hash. Distributed inbox replay is future scope.
10. Cross-tenant record/action: 404; cross-tenant foreign keys cannot be formed.
11. Mid-migration failure: PostgreSQL migration transaction rolls back; earlier migration remains applied. Dedicated regression test included.
12. Backup restore: restore script targets a new recovery database and prints reconciliation counts. Execution drill pending because Docker is unavailable here.
13. Closed accounting period: completion/dispatch/receipt postings fail and roll back atomically.
14. Offline inter-factory transfer: unsupported and not advertised. Future implementation must use in-transit custody.
15. Restricted self-approval: denied, including when creator is ADMIN; another authorized user must approve.
16. Purchase invoice above the order price: payables carry the billed amount, GRNI clears at receipt cost, the difference is a balanced purchase price variance; over-billing a receipt is refused.
17. Supplier return after partial invoicing: the uninvoiced part reverses GRNI, the invoiced part reduces payables; GRNI of a fully processed receipt nets to exactly zero (`procurement.SupplierReturnTest`).
18. Legacy single-item purchase orders and receipts migrate to header + line with posted values unchanged (`procurement.ProcurementMigrationTest`).
19. BOM cycle across levels (A → B → A, or deeper): approval rejected with the cycle path; the revision stays a draft.
20. Parent BOM with a semi-finished component that has no approved BOM: approval rejected until the component's revision is approved (bottom-up).
21. Child order for a shortage: quantity = requirement − released stock − open child supply; a second run finds nothing short (409); the same key replays the first result.
22. Child output satisfies the parent: after final QC releases the child's SF lot, the parent's reservation allocates it FIFO with the older stock; issue consumes it.
23. Parent link tampering: changing `parent_order_id` is rejected by the database trigger.
24. Approved routing tampering: updating or deleting an approved routing, its operations or alternates is rejected by database triggers; only an approved revision can be current (`routing.RoutingTest`).
25. Routing self-approval: the author and the last editor of a draft cannot approve it, ADMIN included.
26. Operation sequence: operation N+1 cannot start before N is done; an order not yet released cannot start operations; quantities never exceed the previous operation's good output (`manufacturing.OperationTrackingTest`).
27. One running operation per work center: a second start on a busy work center is refused (also enforced by a unique index on open time logs); a work center under MAINTENANCE refuses starts, and pausing never overwrites MAINTENANCE.
28. Missing, expired or too-low skill: an operator is refused; a planner/administrator starts only with an override reason, recorded on the time log and audited.
29. Orders without a routing keep the exact pre-V10 lifecycle (create → approve → reserve → issue → start → pause/resume → output → QC → close) and never change work-center status.
30. Calendar maths: breaks, overnight shifts split across days, holidays cancelling the shifts that start that day, overtime (including across midnight and on a holiday) counted once, assigned vs plant-default calendars, around-the-clock without a calendar (`routing.CalendarServiceTest`).
31. Overlapping downtime on one machine (a second open event, or a closed event inside another): refused (409); back-to-back events are allowed (`maintenance.DowntimeTest`).
32. Editing or deleting a closed downtime event: refused by the database; a planner's correction supersedes it and records the corrected or withdrawn event, and only effective events count in metrics.
33. Starting maintenance while an MO is in progress or partially completed on the machine (for a routed V10 order: while one of its operations is in progress there, `maintenance.RoutedOperationMaintenanceTest`): refused with the MO number until a planner pauses it; one work order in progress per machine.
34. Self-approval of a maintenance request: refused, also for ADMIN.
35. "Generate due work orders" twice (or retried): one preventive order per plan and due date; a retry with the same key replays the first result.
36. Spare-part issue beyond released, unreserved stock or in a closed period: refused with no ledger or journal rows; returns put parts back into the issuing lot at the issue value and the expense journal nets to the parts actually used.
37. Plan-driven inspection (V12): a critical characteristic out of specification fails the decision even when the inspector chose pass; a non-critical one passes only with a deviation note; inspections without a plan behave as before (`quality.InspectionPlanTest`).
38. Scrap disposition in a closed period: refused, nothing posted (`quality.NcrDispositionTest`).
39. Concession requested and approved by the same person (ADMIN included): refused.
40. Dispositions above the affected quantity: refused; a rejected concession frees its quantity.
41. Rework value conservation: output lot value = input value + material + labour, rework WIP nets to zero per order and the database `CHECK` enforces it; input → output lot links are immutable.
42. CAPA closed by its owner: refused; a different quality user verifies effectiveness (`quality.CapaTest`).
43. Two-step sign-in code step (V17): after a correct password of an account with two-step sign-in on, every route except identity, CSRF, config, sign-out and `/auth/mfa/verify` answers 403 `MFA_REQUIRED`; a correct code completes the sign-in under a new session id; a waiting sign-in expires after 5 minutes (401) (`platform.MfaTest`).
44. Replayed authenticator code: the same 30-second code is refused (409) on a second sign-in; the next code works. A recovery code works once, case-insensitively; replacing the codes makes every earlier code fail.
45. Guessing codes: 5 wrong codes for one account within 15 minutes → further attempts, even with the right code, get 429 until the window passes.
46. Administrator without two-step sign-in in a real workspace: every route except identity, CSRF, config, sign-out, password change and set-up answers 403 `MFA_SETUP_REQUIRED`, also for a user promoted to ADMIN mid-session; an administrator cannot turn it off (409). The demo workspace and the persona switch are exempt.
47. Turning it on needs the set-up secret of this session, the current password and a correct code; the secret is stored only encrypted (`v1:` prefix, never the Base32 secret) and the user's other sessions end.
48. Administrator reset of a lost phone: not for yourself (409), not across tenants (404), not by a non-administrator (403); removes the secret and recovery codes, signs the user out (401 on their next request) and is audited `USER_MFA_RESET`.
49. TOTP arithmetic: the RFC 6238 SHA-1 test vectors, one step of clock drift either way and nothing further (`platform.TotpTest`).
50. Chart of accounts (V24): every company, existing (migration) or new (tenant trigger), has the standard chart with a system account for every posting code and the reserved Phase 4 codes; any other code found in older journal lines becomes a review account (debit balance → expense, credit or zero → liability) (`accounting.ChartOfAccountsTest`).
51. Journal line on an unknown account: refused at commit by the deferred foreign key, the whole transaction rolls back; on a header or inactive account: refused immediately (`accounting.PostingIntegrityTest`). An entry that is both unbalanced and on an unknown code is reported as unbalanced.
52. Posting date inside a closed period (manual journal, reversal, or a direct insert): refused by the service and the database; system postings keep the pre-V24 guard (a closed period covering today refuses them).
53. Manual journal posting rules: fewer than two lines, debits ≠ credits (to the cent), a line with both or neither side, more than two decimals, a header/inactive/unknown account → refused with the line number; drafts may be incomplete (`accounting.ManualJournalTest`).
54. Manual journal self-approval: the creator, the last editor and the submitter cannot approve it, ADMIN included (409; also a database `CHECK`); roles the `MANUAL_JOURNAL` policy does not name get 403; below the policy threshold or with approval off, submitting posts it and audits *auto-approved by policy*.
55. Approve retried with the same key: one MANUAL entry, the stored result is replayed; the key reused for another command → 409.
56. Posted journals are frozen: no edit or cancel (409; the database refuses updates and deletes); a correction is a reversal.
57. Reversal: any posted SYSTEM or MANUAL entry once, never a REVERSAL; same lines with debit and credit swapped, the same reference, dated on or after the original in an open period; a second reversal is refused by the service and the unique index (`accounting.ReversalTest`).
58. Trial balance: total debits = total credits = the sum of every posted line; each account's closing balance equals the sum of its lines; a period trial balance carries opening + movements = closing (`accounting.TrialBalanceAndLedgerTest`).
59. Account ledger: the opening balance before the range and the running balance continue correctly across keyset pages.
60. FINANCE role: reads and writes the Accounting page, closes and reopens periods, reads Costs & reports and the Overview's financial figures; no user administration, policies or operational writes. Every other role gets 403 from `/api/accounting/**` (`accounting.FinanceRoleTest`, `RoleAccessMatrixTest`).
